Desde PowerShell Windows x64 en la raiz del proyecto:

```powershell
powershell.exe -NoProfile -File .\tools\windows\Initialize-Toolchain.ps1
. .\tools\windows\Use-Toolchain.ps1
git --version
dotnet --version
postgres --version
node --version
npm.cmd --version
powershell.exe -NoProfile -File .\tools\windows\Test-Toolchain-Guards.ps1
```

Se pueden preparar componentes por separado con `-Component git` o `-Component dotnet,postgresql,node` cuando se llama desde PowerShell. No requiere elevacion. Necesita Internet por HTTPS para archivos ausentes; con todos los ZIP en `.local/downloads` se reutilizan despues de comprobar sus hashes. La validacion Authenticode depende de la confianza y certificados del Windows anfitrion; no se promete una instalacion totalmente offline.

`development/toolchain.lock.json` fija Git 2.55.0.windows.5, SDK .NET 10.0.401 (coincidente con `development/server/global.json` y sin roll-forward), PostgreSQL 17.11 revision EDB 4, Node 24.21.0 LTS y npm 11.19.0. RC9 requiere esbuild 0.25.10; no fija otra version Node. Se selecciona la linea LTS 24 y se conserva el lockfile RC9. El build del frontend se ejecutara mediante `npm.cmd ci` en la copia de trabajo asignada, nunca en RC9 adoptada.

Fuentes oficiales y comprobaciones:

- Git: [pagina del proyecto](https://git-scm.com/install/windows), ZIP MinGit de git-for-windows, SHA256 de la API oficial de releases; `git.exe` Authenticode valido, Johannes Schindelin.
- SDK: [Microsoft .NET 10](https://dotnet.microsoft.com/en-us/download/dotnet/10.0), ZIP y SHA512 en el [metadato oficial](https://dotnetcli.blob.core.windows.net/dotnet/release-metadata/10.0/releases.json); `dotnet.exe` firmado por Microsoft.
- PostgreSQL: [canal Windows PostgreSQL](https://www.postgresql.org/download/windows/) remite a [binarios EDB](https://www.enterprisedb.com/download-postgresql-binaries). El SHA256 exacto procede de [respuesta en el repositorio oficial EDB](https://github.com/EnterpriseDB/edb-installers/issues/706#issuecomment-5774581917). `postgres.exe` de este ZIP no esta firmado: se declara `NotSigned` y se exige el hash del archivo completo. No se afirma firma Authenticode PostgreSQL.
- Node: [Node 24 LTS](https://nodejs.org/en/download/archive/v24), [SHA256 oficial](https://nodejs.org/dist/v24.21.0/SHASUMS256.txt) y firma Authenticode OpenJS Foundation. No se afirma verificacion GPG del manifiesto.

El script falla ante hash, firma o version inesperados, desacuerdo con `global.json`, ruta fuera de `.local` o directorio parcial. No sustituye versiones ni borra archivos para esconder un fallo. Los archivos parciales se conservan para diagnostico. Un cambio deliberado de version exige revisar el lock y registrar su motivo y nuevas pruebas. `Use-Toolchain.ps1` modifica PATH y caches solo en el proceso actual.

El ejecutable principal extraido o reutilizado se compara tambien con su entrada dentro del ZIP verificado antes de ejecutarse. `Test-Toolchain-Guards.ps1` crea un fixture nuevo en `.local` y comprueba tres rechazos con codigo 1: desacuerdo del SDK, archivo cache corrupto y directorio parcial; el archivo testigo previo debe sobrevivir intacto. Los fixtures se conservan sin borrar automaticamente.

La activacion fija `DOTNET_GENERATE_ASPNET_CERTIFICATE=false` para evitar certificados de desarrollo automaticos. El primer build de otra tarea ya genero un certificado de desarrollo antes de esta correccion; no se elimina ni se considera HTTPS de produccion. Para el restore bloqueado se debe usar la fuente oficial explicitamente: `dotnet msbuild RackClick.sln -t:Restore,Build -p:Configuration=Release -p:RestoreLockedMode=true -p:RestoreSources=https://api.nuget.org/v3/index.json -m:1 -nr:false -v:minimal`, desde `development/server` y con el entorno activado. Este script de herramientas no ejecuta el build.

La preparacion no crea bases, cuentas PostgreSQL, servicios, certificados, reglas firewall ni modifica PATH global. El laboratorio independiente se gestiona por `development/server/tests/pg_support.py`; comandos en `development/server/tests/README-WINDOWS.md`. `.local` esta excluida de Git y contiene binarios/cache/datos privados que no deben entrar en un paquete de desarrollo.

Evidencia nueva Windows: `evidence/s1-20260928/windows/`. Los logs anteriores Linux y la recepcion R0 se conservan como historicos. La prueba actual de herramientas no certifica servicio Windows, privilegios minimos de produccion, HTTPS, backup/restore ni instalacion limpia sin prerrequisitos; requieren sus ensayos propios.

Verificacion conjunta de desarrollo: `python -B tools/windows/Verify-Windows.py --scope foundation` o `--scope inventory`, siempre con codigo estable y sin otro build simultaneo. `--preflight-only` valida unicamente versiones y entradas, no ejecuta suites. Cada corrida crea evidencia exclusiva y falla ante cambios de fuentes o comandos fallidos; no sobrescribe resultados previos.

El runner y los escenarios de navegador usan un [Job Object de Windows](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) privado con `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Un proceso intermediario espera antes de lanzar el comando hasta quedar asignado al job; un timeout o error cierra solo ese arbol de procesos. No se termina nada por nombre. `tools/tests/test_windows_job.py` prueba codigos de salida, rechazo de asignacion, timeout y descendientes restantes, comprobando que un proceso ajeno creado como testigo sigue vivo. Evidencia propia: `evidence/s1-20260928/windows-process-control/`. No implica que un cluster interrumpido haya hecho apagado limpio; una corrida con timeout falla y conserva su directorio privado para diagnostico.
