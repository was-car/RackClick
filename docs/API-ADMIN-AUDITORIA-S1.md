`GET /api/v1/admin/audit?limit=50&beforeId=<eventId>&actorId=<actorUuid>&resourceId=<resourceUuid>` exige sesión vigente y `security.manage` GLOBAL del mismo Systemhaus, incluso antes de validar consulta/buscar cursor. Concesiones limitadas a clientes/grupos de clientes no habilitan esta lectura administrativa. No se añade una nueva capacidad implícita. Anónimo/vencido401; sin autoridad global403; con autoridad, consulta inválida422 `request_invalid`, cursor ausente, ajeno o fuera de los filtros404 `not_found` indistinguibles.

Respuesta200 y ETag entre comillas:

```json
{"revision":1,"events":[{"id":"UUID","occurredAt":"UTC ISO8601","actor":{"id":"UUID","userName":"nombre actual"},"requestId":"UUID","action":"tipo de operación","resourceId":"UUID"}],"nextBeforeId":null}
```

Se proyectan sólo esos campos: no before_json/after_json, payload de operación, contraseña/hash, token, cookie, CSRF, IP, cadena de conexión ni campos arbitrarios anidados. La procedencia/acción/IDs del evento quedan literales. El nombre del actor es el nombre ACTUAL guardado, no un nombre histórico inventado. No se deducen cliente, diferencias, revisiones de inventario o resultado detallado de JSON genérico en esta primera lectura; esos requisitos del contrato completo permanecen pendientes. Un evento mostrado acredita la fila transaccional persistida; no registra intentos fallidos, login/logout ni cancelaciones si los escritores existentes no generaron ese evento.

Parámetros opcionales: `limit` omitido=50, dígitos ASCII, rango1–100; vacío/repetido/signo/espacio/fracción/desbordamiento inválidos. `beforeId` omitido inicia por más recientes; presente exige UUID D no vacío. Vacío/repetido/malformado/UUID cero inválidos. Filtros43: actorId y resourceId son opcionales; cuando aparecen deben ser UUID D de36caracteres, no cero, sin espacios/llaves/formatoN. Se aceptan letras hexadecimales mayúsculas o minúsculas. Vacío, repetido o malformado devuelve422 tras comprobar permiso global. Se combinan con AND y comparan exclusivamente a.actor_id/a.resource_id dentro del propio Systemhaus, con parámetros SQL tipados. No buscan por nombre, gn, jerarquía, cliente padre, rack padre ni todos los objetos afectados por un lote: resourceId es sólo el ID principal registrado en el evento.

No se consulta si el autor/recurso existe actualmente o está activo; IDs con cero eventos propios devuelven200 con events[] y nextBeforeId:null, incluidos IDs desconocidos o sólo registrados en otro Systemhaus. Si el mismo UUID aparece en eventos de varias instalaciones, sólo coinciden los eventos propios. El nombre presentado del autor sigue siendo el actual. No hay búsqueda por texto, filtros de cliente/fecha/tipo, descarga ni endpoint de diferencias todavía. Otros parámetros siguen sin usarse.

Orden total PostgreSQL `occurred_at DESC,id DESC`. Cursor exclusivo por ID existente del mismo Systemhaus y que satisfaga TODOS los filtros presentes; un cursor fuera de la selección devuelve404 igual que uno ausente/ajeno. Al cambiar filtros, iniciar sin beforeId. Cursor y lista usan el mismo predicado AND;  la consulta recupera su timestamp de la base y busca la tupla anterior. Nunca confiar en timestamps suministrados por el cliente. Se leen `limit+1` filas para emitir `nextBeforeId` igual al último ID MOSTRADO sólo si existe otra página; al agotar, null, incluida lista vacía. Sin offsets ni total global.

Cada página/autorización/nombres/revisión pertenecen a una transacción RepeatableRead; páginas distintas son lecturas nuevas. Nuevos eventos pueden aparecer al volver al inicio; no se promete un snapshot que atraviese páginas ni un feed completo en tiempo real. La marca temporal actual usa la semántica existente de escritura, no representa necesariamente el orden de commits. No modificar eventos/fechas vía SQL durante navegación normal. No hay retención/borrado de auditoría mediante esta API. No se acredita rendimiento sobre millones de eventos ni se añade índice/migración en este bloque.

`revision` y ETag son la revisión de Systemhaus, NO una versión global de auditoría: el inventario tiene revisiones de cliente independientes. No usarlos para afirmar que no hay eventos nuevos, para If-None-Match/304 ni para autorizar acciones posteriores. La autorización se comprueba otra vez en el servidor en cada llamada. GET seguro sin CSRF de mutación; exige la cookie vigente. No incrementa revisión ni crea evento/sesión/operación.
